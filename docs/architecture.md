# OA Practice Platform Architecture

## Directory Structure

The repository is structured to maintain a strict separation of concerns, ensuring modularity and long-term maintainability:

```text
/
├── frontend/        # React + Vite + Tailwind application
├── backend/         # Go REST API and core business logic
├── database/        # Migrations (goose) and queries (sqlc)
├── questions/       # JSON files representing the question bank
├── scripts/         # Utility scripts (e.g., seeding, deployment)
└── docs/            # Architectural and developmental documentation
```

### Backend Structure
Following Clean Architecture principles:
- **`handlers/`**: HTTP handlers that parse requests and format responses.
- **`services/`**: Core business logic and orchestration.
- **`repositories/`**: Database interactions generated by `sqlc`.
- **`models/`**: Domain types (if required outside of sqlc structs).
- **`runner/`**: Abstractions for executing code (C++, Python, SQL).
- **`database/`**: Database connection management.
- **`middleware/`**: Request logging, error recovery, CORS, etc.

## Data Model

The application uses PostgreSQL with the following core entities:

### 1. `questions` (Loaded from JSON into DB, or purely JSON)
For the MVP, questions are loaded from JSON files. They contain:
- ID, Title, Difficulty
- Statement, Constraints, Examples
- Function Signature / Table Schemas
- Type (DSA, Python, SQL)

### 2. `attempts`
Records an entire mock test session.
- ID, StartTime, EndTime, Status (InProgress, Submitted)

### 3. `results`
Records individual question submissions within an attempt.
- ID, AttemptID, QuestionID, Code, Language, Result (Pass/Fail), ExecutionTime, SubmissionTime

## Request Lifecycle

1. **Frontend**: User clicks "Run Tests" or "Submit". The React application sends a REST API request containing the code, language, and question ID.
2. **Handler**: The Go backend (`handlers/`) receives the request, decodes the JSON payload, and calls the appropriate service.
3. **Service**: The service (`services/`) retrieves the question details (hidden/visible tests) and forwards the request to the `runner` module.
4. **Runner**:
   - **C++**: Saves code to a temporary file, compiles it using `g++`, executes the binary with test case inputs, and captures stdout/stderr.
   - **Python**: Saves code, executes using `python3`, and captures stdout/stderr.
   - **SQL**: Creates a temporary PostgreSQL schema, sets up tables, inserts data, runs the user query, compares results against expected output, and finally drops the temporary schema.
5. **Response**: The runner returns structured results (pass/fail, execution time, output) to the service, which formats them and sends them back to the frontend via the handler.

## Technical Decisions

### Database Tools (`sqlc` and `goose`)
- **`goose`**: Used for database migrations to keep schema changes version-controlled, repeatable, and automated.
- **`sqlc`**: Compiles SQL queries into type-safe Go code. It eliminates boilerplate and prevents SQL injection while maintaining raw SQL performance. No ORM is used to avoid unexpected query generation.

### SQL Isolation (PostgreSQL Schemas)
To safely evaluate SQL questions without polluting the main database, the `runner` creates a temporary PostgreSQL schema for every test run. This isolates the evaluation environment, prevents side effects on the primary tables, and allows parallel execution without conflicts.

### Runner Abstraction
The execution logic is abstracted behind a common `Runner` interface (e.g., `Run(code, tests)`). This abstraction allows new languages or sandboxing mechanisms (like Docker) to be introduced in the future without modifying the core service logic.
